Security & Technology Risk Report

Math Competition Readiness Hub · vineetagrwal.github.io/math-dance-pathway · Prepared Nov 2026 · Classification: Internal

Executive summary

A static, single-page web application (plus a Jersey City data pilot) hosted on GitHub Pages. It holds no backend and no sensitive data store, so the attack surface is narrow and centered on client-side and supply-chain risk. Since the initial build, the Medium-severity web risks have been remediated (DOM-XSS, missing SRI, no CSP) and a clean secret scan was confirmed. Residual items are low-severity hardening tasks. Reaching enterprise-grade for global, high-demand access primarily requires fronting the site with a CDN/WAF (for real HTTP security headers, DDoS protection, and rate limiting), a strict CSP, automated dependency monitoring, and a documented data-governance/privacy posture for the school registry.

1. Original state & baseline risk

  • Architecture: one static index.html on GitHub Pages; no server, no database, no auth.
  • Baseline gaps identified: external links without rel="noopener" (tabnabbing); a dead third-party counter (countapi.xyz); no README/LICENSE; no CSP; CDN assets without Subresource Integrity (SRI); DOM-XSS exposure once external data (school names) was rendered via innerHTML; no automated dependency/secret scanning.
  • Baseline posture: low data-breach risk (no data store) but several Medium client-side/supply-chain weaknesses and no hardening baseline.

4. Resiliency & scale posture

  • Strengths for global high demand: fully static assets served from GitHub's CDN — horizontally scalable, no backend to overload, no database to fail. A traffic spike serves cached files; cost stays flat.
  • Single points of failure: GitHub Pages availability; CDN dependencies (unpkg/Leaflet, OpenStreetMap tiles, GoatCounter). Tile/analytics outages degrade gracefully (map/analytics only).
  • No rate limiting / WAF / DDoS controls at the edge today (GitHub Pages provides basic protection only).

5. Hardening roadmap — to enterprise-grade, global access

Phase 1 — Edge & headers (highest impact)

  • Front the site with a CDN/WAF (e.g., Cloudflare) to add HSTS, X-Frame-Options/frame-ancestors, X-Content-Type-Options, Referrer-Policy, plus DDoS protection, rate limiting, and bot management for high-demand access.
  • Self-host or SRI-pin all third-party assets; add a tile-provider fallback.

Phase 2 — App hardening

  • Externalize JS/CSS and adopt a nonce/hash-based CSP (remove unsafe-inline) — closes V-04.
  • Replace mailto: with a vetted form backend (spam/abuse controls, CAPTCHA) — closes V-06.

Phase 3 — Supply chain & CI

  • Enable Dependabot + SCA (e.g., pip-audit) and a link-checker in CI — closes V-08.
  • Add branch protection, required reviews, and signed commits.

Phase 4 — Data governance, privacy & compliance

  • Formalize the registry data pipeline: source attribution, review-before-publish, and a correction/audit trail.
  • Given the education context, document a privacy posture (COPPA / FERPA-aware): collect no student PII; keep submitter data minimal and consented; publish a privacy notice.
  • Accessibility (WCAG 2.1 AA) and a performance budget as release gates.

Phase 5 — Operations

  • Uptime/synthetic monitoring + alerting; a lightweight incident-response runbook; periodic re-assessment.
